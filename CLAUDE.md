## Project overview

**ERP - Modul WMS** (product/app name, `APP_NAME` in `.env`; rebranded 2026-09-06 — was "WMS FullSpec"). This is not a standalone WMS: it's the procure-to-pay module of an ERP, built as a Laravel 12 / PHP 8.2+ / MySQL modular monolith connecting warehouse, procurement, finance, and accounting into one controlled flow: request → PO → LPB (receipt) → multi-warehouse stock → NPK (usage) → supplier invoice → payment → GL journal. Stock movements and financial postings are not administrative side notes — they drive inventory value, FIFO layers, payables, and the general ledger together (perpetual inventory, not periodic — every movement posts a journal entry immediately, the hallmark that puts this in ERP territory rather than a bare warehouse-execution WMS). The rebrand is naming/branding only (`.env` `APP_NAME`, login/sidebar UI text, README.md/feed.MD titles) — no internal code was touched: `wms_` table prefix, `Wms*` class names (e.g. `WmsAccountingService`), the `wmsDataTable()` JS helper, and the "WMS Control Center" feature name all stay exactly as-is, since those are functional/architectural identifiers, not the product's outward branding.

Business-level documentation is bilingual Indonesian/English in [README.md](README.md) (product overview) and [feed.MD](feed.MD) (technical reference — role matrix, domain flows, database tables, WMS control framework, technical debt; refreshed 2026-09-06 to match the renamed schema, the `accounting_manager` role, and every feature listed below). Read `feed.MD` section 15 ("Source of truth") when docs and code disagree: migration > policy > controller+form request > service > model > tests.

## Architecture rules (enforced by `tests/Unit/ArchitectureConventionTest.php`)

These are hard constraints, not style suggestions — the architecture test fails the build if violated:

- **Class/file casing**: class name must exactly match its filename (case-sensitive), checked against both PHP reflection and actual Git-tracked paths — not just the local filesystem (Windows is case-insensitive, so a local mismatch won't show until CI/Linux).
- **No inline validation in controllers**: controllers must not call `->validate(...)` directly; all validation goes in `app/Http/Requests` Form Request classes.
- **Routes are split by domain** and required from `routes/web.php`: `auth.php`, `administration.php`, `warehouse.php`, `procurement.php`, `finance.php`, `accounting.php`, `assets-and-services.php`. Routes must stay `route:cache`-able.
- **Status columns are uppercase machine codes** (e.g. `PENDING`, `APPROVED`, `POSTED`, `VOID`) — never lowercase or mixed case in the database. Indonesian-language labels belong only in the presentation layer.
- **No floating point for business data** in migrations (`$table->double(...)` is banned) — use fixed-point: quantities `DECIMAL(18,6)`, unit cost `DECIMAL(18,4)`, money `DECIMAL(18,2)`, rates `DECIMAL(8,4)`.
- **No legacy table names** (`admin_namagudang`, `invoicelpbs`, `invoicelpbdetails`, `lpbdetails`, `kategoribahan`) may reappear in migrations.
- Table names are plural `snake_case`; new foreign keys follow `<model>_id`.

## Frontend conventions (Tailwind + daisyUI + Alpine, since 2026-09-01)

The UI was fully migrated off Bootstrap 5 / jQuery / DataTables.js — there is zero jQuery or Bootstrap JS in the codebase now. Keep it that way for any new view or edit:

- **Stack**: Tailwind CSS + daisyUI components, compiled via Vite (`resources/css/app.css`, `resources/js/app.js`). Interactivity is Alpine.js, not jQuery.
- **Server-side tables**: list pages talk to the existing Yajra (`datatables()->of(...)`) JSON endpoints through the reusable `wmsDataTable()` Alpine factory (`resources/js/data-table.js`) — do not reintroduce DataTables.js. Row markup is a Blade `<template x-for>`, not server-built HTML strings.
- **Modals**: use a native `<dialog class="modal">` + `.modal-box`, opened via `openAjaxModal()` / closed via `closeAjaxModal()` (`resources/js/ajax-modal.js`), not Bootstrap's `data-bs-toggle="modal"`.
- **Simple CRUD forms**: use `submitAjaxForm($event)` / `confirmAjaxDelete($event, message)` instead of writing a new `$.ajax` handler per view.
- **Searchable `<select>`**: add `data-app-picker` — `resources/js/smart-picker.js` auto-enhances it (no jQuery involved).
- **`.modal-box` must scroll, never clip**: it has a global `max-height` + `overflow-y: auto` in `app.css` specifically so a tall form's footer buttons stay reachable instead of being cut off — don't override that with a fixed height or `overflow-hidden` on a per-view basis.
- **Responsiveness is a hard requirement, not an afterthought.** Every new or edited view must be checked at mobile width, not just desktop: use Tailwind's responsive prefixes (`sm:`/`md:`/`lg:`) on grids and flex layouts instead of a single fixed multi-column layout, wrap any wide table in `overflow-x-auto`, and actually resize the browser (or check devtools' responsive mode) before calling a view done — do not assume a desktop-only render is good enough.

Cross-model processes (posting a document, reversing it, computing FIFO cost) belong in `app/Services`, not controllers. Gates (`AuthServiceProvider`) are used only for capabilities that span multiple models (e.g. `viewWmsControl`, `operateWarehouse`); everything else uses per-model Policies.

Stock and accounting mutations are wrapped in `DB::transaction()`; operations prone to races use `lockForUpdate()`.

## Authorization model

- `users.type` is a foreign key into `user_roles` (roles are no longer bare integers). Seven roles: `super_admin`(0), `purchasing`(1), `finance`(2), `warehouse`(3), `accounting`(4), `production`(5), `accounting_manager`(6, added 2026-09-05 — approves supplier invoices only, see "maker-checker" gap entry below).
- `SuperAdmin` bypasses all policies via `Gate::before` in `app/Providers/AuthServiceProvider.php` — do not add redundant SuperAdmin checks inside individual policies.
- `User` model exposes role helpers: `isSuperAdmin()`, `isPurchasing()`, `isFinance()`, `isWarehouse()`, `isAccounting()`, `isProduction()`, `isAccountingManager()`, `isWarehouseOperator()`, plus warehouse-scoping helpers `accessibleGudangIds($ability)` and `canAccessGudang($gudangId, $ability)`.
- `Produksi` (production) role is scoped to specific warehouses via the `pembagian_gudangs` table (fields: `boleh_menerima`, `boleh_npk`, `boleh_transfer`, `boleh_opname`). `Warehouse` role has access to all active warehouses; `Produksi` only to assigned ones. Controllers filter warehouse-scoped lists through `accessibleGudangIds()`.
- Newer policies (`PemakaianBarangPolicy`, `TransferGudangPolicy`, `StockOpnamePolicy`, and others) follow a pattern of private "who is allowed" / "warehouse access" helper methods, with public `view/create/update/...` methods below — follow this pattern for new policies.

## Domain concepts to know before editing warehouse/inventory code

- **Warehouse types** (`Gudang` model constants): `NORMAL`, `CONSIDER` (quarantine), `RUSAK` (damaged, terminal state).
- **Document lifecycles**: Material Request `PENDING → APPROVED/REJECTED`; Purchase Order `OPEN → CLOSED`; LPB/BAP and NPK `DRAFT → POSTED → REVERSED` (or `CANCELLED`); Invoice `UNPAID → PARTIALLY_PAID → PAID` (or `VOID`); Payment `POSTED → VOID`; Transfer `DRAFT → DIAJUKAN → DIKIRIM → DITERIMA` (or `DIBATALKAN`); Stock Opname `DRAFT → SUBMITTED → APPROVED → POSTED` (or `REJECTED`). **Posted documents are immutable** — corrections always go through a controlled reversal/void with audit metadata and a reversing journal entry, never edit/delete.
- **FIFO inventory layers** (`LayerPersediaan`): LPB posting creates layers; NPK consumes them FIFO (FEFO-then-FIFO for picking). NPK only consumes layers that are `AVAILABLE`, not blocked, and not expired. Layer statuses: `AVAILABLE`, `QC_HOLD`, `IN_TRANSIT`, `REVERSED`, `TRANSFER_SHORTAGE`.
- **Units**: `Bahan` (material) may have a small/transaction unit distinct from its main stock unit. NPK stores `jumlah` (transaction qty), `jumlah_stok` (converted to stock unit), and `satuan_transaksi` (snapshot of the input unit) — conversion always happens before FIFO consumption.
- **Transfers** preserve layer value across warehouses and use an idempotency key to reject duplicate requests. In-transit stock sits in an `IN_TRANSIT` layer; global company balance is unaffected until received. Internal transfers currently post no journal entry.
- **Journals**: LPB posts debit persediaan (inventory) / credit GRNI. NPK posts debit beban (expense) / credit persediaan. Journal creation is service-layer, not controller-layer.
- **Three-way match**: supplier invoices reconcile PO–LPB–Invoice before an AP journal posts (`ThreeWayMatchService`).
- **Landed cost**: capitalized into active layers and posted balanced to GL (`LandedCostService`).
- **Reconciliation invariants**: master quantity = warehouse + in-transit; warehouse balance = sum of layers; layer value = GL inventory balance.
- The **WMS Control Center** (menu: Multi Gudang → WMS Control Center) is the operational home for traceability (bin/lot/serial/expiry, block/release), warehouse execution (QC, putaway, reservation, FEFO/FIFO picking), financial control (three-way match, landed cost, controlled reversal), and planning (reorder point, safety stock, replenishment).
- **Gudang Produksi** (production warehouse) is a stage-1 feature: `Gudang Utama → Gudang Produksi` moves via ordinary Transfer Gudang (no journal for the internal move); NPK from Gudang Produksi is where material consumption begins. There is no dedicated WIP/manufacturing model yet — production still uses the same direct-consumption-on-NPK pattern as other warehouses.

## Material Request workflow (widened 2026-09-05)

Any role except Purchasing can now submit a Material Request (`MaterialRequestPolicy::create()` — was Purchasing/Warehouse only); Purchasing and Accounting still approve. `requests.requested_by` (migration `2026_09_05_000005_add_requester_and_fulfilled_status_to_requests`) tracks who submitted it, and `MaterialRequestController::index()` scopes the listing to "own requests only" for anyone who isn't a reviewer (Purchasing/Warehouse/Accounting) so every user can track their own request's lifecycle without seeing everyone else's. ## Expiry chain + replenishment-to-request bridge (2026-09-09)

**Expiry chain.** The FEFO/expiry engine was fully built but had no data on-ramp: `expires_at` could only be set through the standalone "Tambah Lot" form in WMS Control Center, while all four LPB receiving requests accepted `lot_number` only. Every lot created by an actual receipt therefore had `expires_at = NULL`, which silently made five separate guards inert — `StokGudangService::ambilLayer()` (the FIFO consumption path NPK uses), `WmsAccountingService`, `StokGudang`, `ReplenishmentService`, and the FEFO ordering in `WarehouseExecutionService::createPick()` — so FEFO degenerated to plain FIFO and expired stock was never actually blocked. Fixed end to end: `StorePenerimaanBarangRequest` now accepts `details.*.expires_at`, `PenerimaanBarangController::store()` passes it into `LotPersediaan::firstOrCreate` **and** back-fills it when an existing lot row still has a null date (without that back-fill, any material whose lot number was already received once could never gain an expiry, since the lookup key is `(bahan_id, lot_number)`); `penerimaan_barang/create.blade.php` gained a "Kedaluwarsa" date column that stays disabled until a lot number is typed. Only `store()` was touched because it is the sole path that creates `LayerPersediaan`/`LotPersediaan` rows — `storeDetail()`/`updateDetail()` write the detail row and `Bahan.stok_onhand` only, and `update()` never re-creates layers. Alerting: `AuthController::expiryCounts()` (stock-aware — counts `AVAILABLE` layers with `remaining_quantity > 0`, not bare lot rows, so fully-consumed expired lots don't raise a false alarm) feeds two new task cards, "Stok Kedaluwarsa" and "Mendekati Kedaluwarsa (30 Hari)", on the warehouse dashboard (all warehouses) and production dashboard (scoped to `accessibleGudangIds('npk')`); both link to WMS Control Center, whose "Lot & Expiry" table is now stock-aware (`withSum` of remaining layer quantity scoped to accessible warehouses), sorted expiring-soonest-first, greys out zero-stock lots, and shows a "Sisa N hari"/"Lewat N hari" badge. Diagnosis: `StokGudangService::pesanLayerTidakCukup()` replaces the bare "Layer persediaan gudang tidak mencukupi." with a message naming how much stock is unusable because it expired or is blocked — previously an operator hit a generic shortage error with no hint that the goods were physically present but expired. Covered by `tests/Feature/WmsControlFrameworkTest.php::test_receiving_captures_lot_expiry_and_expired_stock_is_rejected_with_a_clear_message`.

**Replenishment → Material Request.** `SaranPengisianUlang` rows were computed and listed but were a dead end — the table rendered raw `#gudang_id / #bahan_id` and offered no action, so a planner had to retype the suggestion into a request by hand. Added `ReplenishmentService::createMaterialRequest()` (cross-model, so it lives in the service, not the controller): it creates a `PENDING` `MaterialRequest` with one `RequestDetail` line carrying the suggested quantity plus the material's category/unit snapshot and `tipe_gudang` = the suggestion's warehouse, then marks the suggestion `REQUESTED` and links it via a new nullable `material_request_id` FK (migration `2026_09_09_000001_add_material_request_to_saran_pengisian_ulang`). `calculate()` was switched from `updateOrCreate` to `firstOrNew` + skip so a same-day recalculation cannot reset an already-actioned suggestion back to `OPEN` and invite a duplicate request. Route `wms-control.replenishment.request` → `WarehouseExecutionController::requestReplenishment()`, which catches the service's `RuntimeException` and redirects `withErrors()` rather than 500-ing — the button sits in a table row, so double-submit and stale-page replays are expected, and note the WMS Control Center's `warehouse_partials.alerts` renders `$errors`, not a generic `error` flash key. Suggestions are now eager-loaded with `gudang`/`bahan` and rendered with names, formatted numbers, and a priority badge. Covered by `::test_replenishment_suggestion_becomes_a_material_request_and_is_not_reopened_by_recalculation`.

## Lot control, per-bin putaway, pick-to-NPK, serial lifecycle (2026-09-09)

Backlog items 1–5 from the survey below, done in one pass. All five were gaps in code that already existed, not new domains.

**Lot/expiry is now enforceable per material.** `bahans` gained `wajib_lot`/`wajib_expiry` (migration `2026_09_09_000002`), toggled from the master-bahan edit form and enforced in `StorePenerimaanBarangRequest::after()`, which resolves each detail row's `Bahan` and adds a per-row error naming the material. Without this the `expires_at` field added earlier the same day was purely optional, so one skipped entry silently switched FEFO and every expired-stock guard back off for that receipt. `wajib_expiry` without `wajib_lot` is rejected in `UpdateBahanRequest::after()` rather than silently coerced — expiry is stored on the lot, so that combination is literally unsatisfiable at receiving time. `getPoDetail()` now returns both flags so the receiving form can mark the inputs `required` and highlight them; note the checkboxes need the `<input type="hidden" value="0">` companion because `BahanController::update()` reads them with `$request->boolean()`.

**Putaway is per line, and bin capacity is enforced.** `WarehouseExecutionService::putaway()` now takes `array $locationByDetail` (detail id → location id) instead of a single `LokasiGudang`, validates each location against the LPB's warehouse, and writes `warehouse_location_id` per detail — previously one blanket `update()` dumped every line of a receipt into the same bin. **`wms_lokasi_gudang.capacity` already existed but was dead**: entered via `StoreLokasiGudangRequest`, cast on the model, and read by nothing. `assertLocationCapacity()` now blocks a putaway that would push a bin past its capacity, accumulating per location within the same submission so two lines targeting one bin are checked against their combined total. Capacity is treated as total units in the bin — dimensionally loose across mixed materials, but that is what a single decimal column can express and it beats no check at all. A null capacity still means unlimited.

**Completed picking orders can be issued as a draft NPK.** `wms_pemakaian_barang` gained `picking_order_id` (migration `2026_09_09_000003`) and `WarehouseExecutionService::createDraftIssue()` turns a `COMPLETED` pick into a `DRAFT` `PemakaianBarang` carrying the picked quantity, the reservation link, and the unit snapshot. **Deliberately creates a DRAFT, not a posted NPK**: the entire journal/FIFO/period-lock path already lives in `PemakaianBarangController::update()`'s DRAFT→POSTED branch, so the operator posts it through the normal form and none of that tested accounting logic is duplicated in a second place. The `picking_order_id` FK is also the duplicate guard (`PesananPengambilan::npk()`), and the UI shows the resulting NPK code instead of the button once issued.

**Serial numbers have integrity and a lifecycle.** They were write-only before — created by `WmsTraceabilityController::storeSerial()` and read by nothing. `StoreSerialPersediaanRequest::after()` now refuses to register more serials than the lot actually received (`lot->layers()->sum('initial_quantity')`, skipped when the lot has no layers yet so manually pre-created lots still work), and `PATCH wms-control/serials/{serial}/status` moves a serial between `AVAILABLE`/`ISSUED`/`SCRAPPED`. The control center lists serials with their status and shows an available/total count per lot. This is deliberately *not* serial-level issue tracking inside NPK — NPK is quantity-based, so forcing serial selection there would be a much larger build.

**Fixes from the code review of this same batch (2026-09-09):** the bin-capacity loop originally kept a `$rencanaPerLokasi` accumulator *and* re-read the bin's current fill, but each line's layers are written before the next line is checked — so two lines sharing a bin were counted twice and a legitimate 4+4 into a capacity-8 bin was rejected at 12. The accumulator was removed; the re-read alone is correct. The replenishment "skip REQUESTED" guard was keyed on `calculated_at = today()`, so it only blocked same-day recalculation and the next day produced a fresh `OPEN` row for a shortage whose request was still pending — `ReplenishmentService::permintaanBelumTuntas()` now carries the link forward across days, and `createMaterialRequest()` refuses outright while a `PENDING`/`APPROVED` request exists for that gudang+bahan. Receiving used to silently discard a typed expiry when the lot already had one, which is worse once `wajib_expiry` forces the operator to enter it; a mismatch is now a validation error naming the registered date. `WmsControlController` gained a separate `lotOptions` collection for the "Tambah Serial Number" picker, because reordering `lots` to expiry-ascending pushed undated lots past the `limit(100)` window. `MaterialRequestController::isRequestReviewer()` now includes `isSuperAdmin()` — the raw `hasAnyRole()` check is not a policy, so `Gate::before` never applied and an admin's own list and exports were silently filtered to their own requests (this bug predated the batch in `index()` and had been copied into both report methods).

One review finding was **not** a bug: the serial cap was reported to allow 13 serials on a 10-unit lot with 3 rejected, but `inspect()` reduces the original layer to `initial_quantity = $accepted` before creating the reject layer, so the two layers still sum to the original quantity.

Covered by seven tests in `tests/Feature/WmsControlFrameworkTest.php`: `::test_lot_controlled_material_cannot_be_received_without_lot_and_expiry`, `::test_putaway_places_each_line_in_its_own_bin_and_respects_capacity` (builds its own two-line LPB — no seeded LPB has more than one detail), `::test_completed_picking_order_becomes_a_draft_npk_exactly_once`, `::test_serial_registration_cannot_exceed_lot_quantity_and_status_is_updatable`, plus the review-driven `::test_two_putaway_lines_sharing_one_bin_are_counted_once_against_capacity` and `::test_receiving_rejects_a_reused_lot_number_with_a_conflicting_expiry`. ### Built 2026-09-11: declining-balance depreciation + Laporan Arus Kas

**Saldo menurun (declining balance).** `wms_asets.depreciation_method` already existed but `runAutomaticDepreciation()` filtered `where('depreciation_method', 'STRAIGHT_LINE')`, so any other method was silently skipped and the column was never settable (`StoreAsetRequest` did not accept it, so every asset defaulted to straight-line). Now: `Aset::STRAIGHT_LINE`/`Aset::DECLINING_BALANCE` constants, `suggestedMonthlyDepreciation()` branches on the method, the auto-run accepts both, and the asset form exposes the choice. The declining rate is **2× the straight-line rate applied to the running book value** — monthly `= (book_value − residual) × 2 / useful_life_months`, which reproduces the Indonesian fiscal saldo-menurun rates (Kelompok 1, 48 months → ≈50%/year). The pre-existing `$amount > $maximum` guard in `depreciate()` and the `min($suggested, $maximum)` in the auto-run already handle the terminal period, so no extra clamp was needed. Covered by `AsetDepreciationTest::test_declining_balance_depreciation_charges_double_rate_on_the_running_book_value` (2.4M over 48 months → 100k then 95,833.33).

### Fiscal reconciliation — policy decided 2026-09-11, stage 1 of 3 built

**The user's policy choices (do not re-litigate these; they are accounting decisions, not engineering ones):**
- Classification lives **on the COA with a per-journal-line override** — not COA-only (an account like "Beban Lain-lain" can mix deductible and non-deductible items) and not line-only (too much daily input to stay consistent).
- Commercial vs fiscal depreciation gets a **dual schedule computed automatically** — each asset carries its own fiscal method and fiscal group (Kelompok 1–4) alongside its commercial method, and the system derives the beda-waktu correction itself rather than asking an accountant to type it.
- Target scope is the **full stack including deferred tax (PSAK 46)** — reconciliation report, then PPh Badan (22% + the Pasal 31E 50% reduction), then deferred tax assets/liabilities posted to the GL.
- Permanent differences that actually occur in this business: **sanksi & denda pajak, sumbangan & natura, and income already subject to PPh Final.** Entertainment without a daftar nominatif was explicitly excluded.

**Stage 1 (done).** `wms_bagan_akun.klasifikasi_fiskal` and `wms_jurnal_detail.klasifikasi_fiskal` (migration `2026_09_11_000001`), values `NONE` / `BEDA_TETAP` / `BEDA_WAKTU` / `PENGHASILAN_FINAL`, with the effective classification resolved as `COALESCE(line, account)`. Three COAs were seeded pre-tagged (`5304` Beban Sanksi dan Denda Pajak, `5305` Beban Sumbangan dan Natura → BEDA_TETAP; `4205` Penghasilan Kena PPh Final → PENGHASILAN_FINAL), and `5301` Beban Penyusutan Peralatan was tagged BEDA_WAKTU as the hook for stage 2. `RekonsiliasiFiskalService::reconcile()` computes laba komersial from PENDAPATAN/BEBAN movement in the period, then groups corrections: a BEDA_TETAP expense becomes a koreksi positif, a PENGHASILAN_FINAL or BEDA_TETAP income becomes a koreksi negatif. **Sign convention matters** — expense amounts are `debit − kredit`, income amounts are `kredit − debit`, so both arrive as positive magnitudes before being added or subtracted.

**Rule that still governs BEDA_WAKTU:** a timing difference's correction is **never** the account's book amount — it is the *difference* between commercial and fiscal treatment. Accounts with no fiscal basis to compare against therefore report `koreksi = 0` with `sumber_koreksi = 'MENUNGGU_JADWAL_FISKAL'` and are badged in the UI. Do not "fix" that by adding the book amount into the correction — it would make laba fiskal wrong.

**Stage 2 (done 2026-09-11): dual fiscal depreciation schedule.** `wms_asets` gained `kelompok_fiskal`, `metode_penyusutan_fiskal`, `akumulasi_penyusutan_fiskal`, and `wms_penyusutan_asets` gained `amount_fiskal` (migration `2026_09_11_000002`). `Aset::KELOMPOK_FISKAL` encodes UU PPh Pasal 11: Kelompok 1–4 at 48/96/192/240 months plus Bangunan Permanen (240) and Tidak Permanen (120). **Two fiscal rules that differ from commercial and are easy to get wrong:** fiscal depreciation ignores residual value entirely (the base is full `acquisition_cost`, depreciated to zero), and buildings may only use straight-line — enforced in `StoreAsetRequest::after()`. Fiscal depreciation is **not journalized** (it is a tax computation, not a book entry); it is computed and stored per period alongside the commercial figure inside `AsetAccountingService::depreciate()`, so both schedules always advance on exactly the same periods and the audit trail sits on the same row.

The reconciliation now sources the depreciation timing difference from that schedule: `RekonsiliasiFiskalService::penyusutanPerAkunBeban()` aggregates `amount − amount_fiskal` **grouped by `KategoriAset.depreciation_expense_coa_id`**, not globally — grouping matters because two asset categories can post to different expense accounts, and a single global total would be attributed to each account row and double-counted. Sign convention: `koreksi = komersial − fiskal`, added to laba fiskal, so fiscal depreciation exceeding commercial correctly *lowers* taxable profit. Covered by `::test_fiscal_depreciation_schedule_drives_the_timing_difference`, which measures the *delta* in `total_koreksi_beda_waktu` across a depreciation run rather than an absolute figure — `aset.depreciate-all` also depreciates every seeded asset, so any absolute assertion would be hostage to seed composition.

**Stage 3 (done 2026-09-11): PPh Badan + deferred tax PSAK 46.** `PajakPenghasilanService` computes and (separately) posts. Current tax: PKP is laba fiskal **rounded down to full thousands** (UU PPh Pasal 17 ayat 4), then Pasal 31E splits it — turnover above 50 billion gets no facility; at or below 4.8 billion the whole PKP is facilitated at 11%; in between, the facilitated portion is `PKP × 4.800.000.000 / peredaran bruto` at 11% with the remainder at 22%. A fiscal loss yields zero tax, and since 2026-09-12 it is carried forward (below). Peredaran bruto is an operator input because the system has no sales side to derive it from.

Deferred tax uses the **balance-sheet liability method**, as PSAK 46 requires — not the income-statement approach. The cumulative temporary difference is `book_value − nilaiBukuFiskal()` summed over active assets **that have a `kelompok_fiskal`** (without one there is no tax base, so no difference is computable). Target position = difference × 22%; positive means a liability, negative an asset. The already-recognised amount is read **from the GL balances of the DTA/DTL accounts rather than a stored field**, so it cannot drift out of sync, and the journal moves both accounts to their target (liability target when positive, asset target when negative, the other to zero) with `BEBAN_PAJAK_TANGGUHAN` as the balancing line — that keeps the balance sheet from accumulating offsetting DTA and DTL balances. `wms_perhitungan_pajak_penghasilan` stores one row per `tahun_pajak` (unique) as the audit snapshot and the double-post guard.

New COAs and `AccountingSetting` keys: `HUTANG_PPH_BADAN` (2107), `BEBAN_PPH_BADAN` (5306), `ASET_PAJAK_TANGGUHAN` (**1601**), `LIABILITAS_PAJAK_TANGGUHAN` (2108), `BEBAN_PAJAK_TANGGUHAN` (5307). **Caution learned the hard way:** the first attempt used `1501` for the deferred tax asset, which silently *renamed* the existing "Peralatan dan Inventaris" fixed-asset account — it already carried a 4,000,000 balance and is referenced by `KategoriAset.akun_aset_id` for the EQUIPMENT category, because the seeder uses `updateOrCreate(['kode_akun' => …])`. **Before adding any COA to `DatabaseSeeder`, check the code is genuinely unused** — a collision does not error, it hijacks a live account. Both new expense accounts are tagged `BEDA_TETAP` so income-tax expense is added back in the reconciliation rather than reducing fiscal profit.

**Kompensasi kerugian fiskal 5 tahun (done 2026-09-12).** Per UU PPh Pasal 6 ayat (2) a fiscal loss is offset against profit for the five following tax years. `wms_perhitungan_pajak_penghasilan.kompensasi_kerugian` holds the total applied in a year, and the child table `wms_kompensasi_kerugian_fiskal` (migration `2026_09_12_000001`) records which source year each slice came from — so the remaining balance of any loss year is `abs(laba_fiskal) − sum(kompensasi rows for that tahun_rugi)` and never needs a mutable running field. `sisaKerugian($tahun)` lists unexpired losses (`tahun_pajak` between `$tahun − 5` and `$tahun − 1`) and `pakaiKerugian()` consumes them **oldest-first**, which is both the statutory order and the one that wastes the least before expiry. The offset is applied *before* the thousands rounding, so PKP = `floor((laba fiskal − kompensasi) / 1000) × 1000`.

**Design consequence worth knowing:** `posting()` no longer refuses when there is nothing to journalise. A loss year produces no PPh and often no deferred-tax movement, yet its record **must** exist for the loss to be claimable later — so the computation row is always created and `journal_id` simply stays null when `barisJurnal()` returns nothing. Do not reinstate the "nothing to post" exception; it would make losses uncarryable. Covered by `::test_fiscal_loss_is_carried_forward_fifo_and_expires_after_five_years`, which seeds a 6-year-old loss (must be ignored as expired) plus two live ones and asserts the older is drained first.

Routes `financial-statements.pajak-penghasilan` (GET, simulation) and `.posting` (POST, journalises), view `financial_statements/pajak-penghasilan.blade.php` with a history table. Covered by `::test_pasal_31e_facility_reduces_tax_as_turnover_falls` (asserts tier relationships and the exact 11%/22% endpoints rather than hardcoded rupiah, so it survives seed changes) and `::test_deferred_tax_is_posted_from_the_cumulative_book_versus_tax_base_difference` (2,000,000 difference → 440,000 liability, balanced journal, re-computation then shows zero movement, second posting refused).

Routes `financial-statements.rekonsiliasi-fiskal{,.pdf,.excel}`, view `financial_statements/rekonsiliasi-fiskal.blade.php`, tagged on the COA edit form, added to the statements tab strip. Covered by `FinancialStatementTest::test_fiscal_reconciliation_adds_back_permanent_differences_and_defers_timing_ones`, which posts a journal hitting both a beda-tetap expense and a final-taxed income and asserts the arithmetic ties end to end.

### Service scenarios the business actually runs, and where they land (verified 2026-09-11)

`wms_kategori_jasa` models exactly two kinds — `SERVICE_OPERATIONAL` and `SERVICE_PRODUCTION` — and each maps only to an **`expense_coa_id`** plus a GRNI account. Receipt is progress-based (`wms_penerimaan_jasa_detail.progress_percent`) and allocatable to a `datapesanan_code`. `wms_pelepasan_asets.disposal_type` accepts only `SALE` or `WRITE_OFF`, with `proceeds` assumed to land in a cash/bank COA.

- **Jasa repair/pemeliharaan** — genuinely a service (PPh 23 at 2% covers perawatan/perbaikan mesin, peralatan, listrik, AC, bangunan). Cost recording works today. **Two gaps:** a service category can only post to a *beban* account, so a repair that extends useful life or capacity cannot be capitalized into the asset's carrying amount as PSAK 16 requires; and there is no tracking of our item physically leaving for the vendor and returning (no outbound/gate-pass anywhere in this system).
- **Sewa** — also a service, but the withholding splits: sewa **selain** tanah/bangunan → PPh 23 2%; sewa tanah dan/atau bangunan → **PPh 4(2) Final**. Both PPh types already exist, so the split is supported. The gap is the **loaner/replacement unit** a vendor lends while our item is being repaired: there is no consignment/borrowed-goods model, and booking it into ordinary stock would overstate inventory and assets since the goods are not ours. (If the vendor does not charge for the loaner there is no expense at all — it is purely a custody record.)
- **Tukar tambah (trade-in)** — **not a service.** It is a penyerahan barang via tukar-menukar; per UU PPN Pasal 1A barter remains a PPN object and the DPP uses the **nilai wajar** of the goods exchanged. Classifying it as jasa gets both the DPP and the tax type wrong. The system cannot record it: `disposal_type` has no `TRADE_IN`, an asset disposal has no link to a purchase/PO, and the outgoing leg has no PPN Keluaran account to post to.

  **Correction, from a code read on 2026-09-13: this is NOT actually blocked behind the AR domain, despite what the line above originally implied.** A trade-in needs no piutang and no sales order — the outgoing leg is an *asset disposal*, and the value the supplier credits us can ride the **existing, already-tested supplier-advance mechanism** (`jenis_selisih=UANG_MUKA_SUPPLIER`, `coa_kas_bank_id=null`), the same pattern `WmsAccountingService::applyReturToInvoice()` already uses for a post-invoice retur, so it flows into the new purchase through `available-advances/{supplier}` exactly like an overpayment. The only genuinely missing piece is **one COA plus an `AccountingSetting::PPN_KELUARAN` key** for the output-VAT liability — that is a single account, not the AR/sales domain. Shape of the entry: debit accumulated depreciation and Uang Muka Supplier (DPP + PPN), credit the asset's acquisition cost and PPN Keluaran, with gain/loss measured against **DPP only** (nilai wajar), not DPP + PPN. `wms_pelepasan_asets` would also need `supplier_id` and a link to the offsetting purchase. Building it would *not* deliver e-Faktur output, which does still need the sales side.

## Production-readiness gaps — the platform layer (surveyed 2026-09-12)

Everything above this point is domain work. This section is different: it is what a read-through of the **non-domain** layer found, and it is the reason the system is not yet deployable to real users regardless of how complete the WMS/accounting modules get. None of these were in the backlog before; all were verified in code on 2026-09-12, not recalled.

### Tier 1 — blocks production deployment — ✅ ALL FIVE BUILT 2026-09-12/13, see "Tier 1 platform hardening" below

1. **There is no user management at all.** No `UserController`, no user routes in `routes/auth.php` (it holds exactly login/logout/dashboard), no password-reset flow. The `users` table has `name`/`email`/`password`/`type` and nothing else — **no `is_active`, no soft delete, no `last_login_at`**. Operational consequence: a departing warehouse operator's account cannot be disabled without editing the database by hand. Access control is meticulous above this layer (7 roles, per-model policies, `Gate::before`) while the door itself is unmanaged. Build order when this is tackled: `is_active` + a deactivation path first (that is the security-relevant half), CRUD second, self-service password reset last.
2. **Login is brute-forceable.** `AuthController::login()` calls `Auth::attempt()` with no `throttle` middleware on `POST login`; `RateLimiter` is registered in `RouteServiceProvider` for the `api` group only, which nothing uses. Also **authentication events are not audited** — `Auditable` covers 12 models but there is no record of who logged in, when, or from where, so a credential compromise leaves no trail.
3. **`Kernel::schedule()` is empty** — not one scheduled job exists. Every periodic process is therefore a button a human has to press: `AsetAccountingService::runAutomaticDepreciation()` is a form POST, `ReplenishmentService::calculate()` is a form POST, and expiry/reminder alerts are only computed when someone opens a dashboard. **The system only notices anything when a human clicks.** Note the interaction with the reminder panels built the same day: they are a *pull* surface over data that nothing refreshes on its own.
4. **No notification mechanism of any kind.** There is no `app/Notifications`, `app/Mail`, `app/Events` or `app/Listeners` directory, and `MAIL_MAILER=log`. So approvals wait in silence: a `PENDING` Material Request sits until a reviewer happens to log in, and a `PENDING_APPROVAL` invoice sits until the Accounting Manager happens to look. The maker-checker gate works, but nobody is told their turn has come. Depends on item 6 (a real queue) before email can be sent without blocking requests.
5. **No document attachments anywhere.** Zero `Storage::` calls in `app/`, and no attachment/`lampiran` column in any of the 52 migrations. Nothing can carry the supplier's invoice scan, the signed PO, the supplier's surat jalan, a QC photo of rejected goods, or an asset photo. **For a system that produces journals, financial statements and tax computations this is an audit gap, not a convenience gap** — it holds the numbers with none of the source evidence an auditor asks for. Needs two decisions from the user before building: storage target (local disk vs S3) and per-file size/type limits.

## Tier 1 platform hardening — BUILT 2026-09-12/13

All five Tier-1 items above are now built. Read this section before touching auth, the scheduler, notifications, or attachments — several decisions here are deliberate and look wrong if you only read the code.

**New route file `routes/administration.php`** (added to `routes/web.php` and to `ArchitectureConventionTest`'s required-file list) holds user management, profile, notifications, and attachments. Password reset lives in `routes/auth.php` alongside login.

### 1. User lifecycle

`users` gained `is_active`, `last_login_at`, `last_login_ip`, `deactivated_at`, `deactivated_by` (migration `2026_09_12_000002`). **`is_active`, `deactivated_at` and `deactivated_by` are deliberately NOT in `$fillable`** — an account-state flag must never be settable from request input, so `UserAccountService` writes them with `forceFill()->save()`. This bit once already: `nonaktifkan()` originally used `update()` and the two timestamp columns were silently dropped while `is_active` went through, which is exactly the failure mode mass-assignment protection produces. Note Eloquent **factories bypass guarding** (`Factory::make()` wraps in `Model::unguarded()`), so `User::factory()->create(['is_active' => false])` still works in tests, and a **query-builder** `User::where(...)->update([...])` bypasses it too — only *model* `update()`/`fill()` is guarded.

`App\Services\UserAccountService` owns create/update/deactivate/reactivate/password plus the audit writes. Two guards: you cannot deactivate your own account, and the **last active Super Admin cannot be demoted**. The lockout guard lives in `perbarui()` (role change), which is where it actually matters — going through `nonaktifkan()` it is unreachable by construction, since the actor must be an active Super Admin to pass the policy, so a second active Super Admin always exists. It is kept in both places as defence in depth. Deactivation also deletes the user's Sanctum tokens.

`UserPolicy` returns **false from every method except `view` (self only)** — that is not dead code. Super Admin reaches everything through `Gate::before`, so an all-false policy is precisely how "Super Admin only" is expressed under this repo's rule against redundant Super Admin checks inside policies. `view`-on-self exists so the profile page has a policy answer.

Self-service is split into `ProfilController` (own identity + own password, no policy needed since it is always self) rather than overloading `UserController` with two different authorization models.

### 2. Login hardening

`POST login`, and all three password-reset endpoints, now carry `throttle:login` — a named limiter in `RouteServiceProvider` with **two tiers**: 5/min per `email|ip` and 20/min per IP, so one attacker cannot lock out an entire office by hammering one address, and spraying many addresses from one IP is still capped.

**Deactivated accounts are checked before `Auth::attempt`, not after.** `akunNonaktifDenganKredensialBenar()` queries `where('is_active', false)` first and only then runs `Hash::check`, so the expensive hash only happens for the rare inactive-account case and the ordinary login path pays one cheap indexed SELECT. Doing it after a failed attempt instead would have written **two** audit rows for one attempt (`login_gagal` from the `Failed` event plus `login_ditolak`) and hashed twice. The specific "akun dinonaktifkan" message is only shown when the password is also correct, so it leaks no account state to someone guessing.

`Auth::attempt($credentials + ['is_active' => true])` is the actual enforcement — an inactive user cannot authenticate even if the pre-check is ever bypassed.

Auditing hangs off Laravel's own auth events (`Login`/`Logout`/`Failed` → `App\Listeners\CatatAktivitasAutentikasi`, registered in `EventServiceProvider`) rather than being inlined in the controller, so **every** authentication path is covered, not just this one form. Rows go into the existing `wms_log_audit` with `event` ∈ `login` / `logout` / `login_gagal` / `login_ditolak`. Migration `2026_09_12_000003` makes `auditable_id` nullable — a failed login for an unknown email has no subject, and the attempted address is kept in `metadata`. Viewable at `user.login-audit`.

Password reset uses Laravel's broker with `['email' => …, 'is_active' => true]` as credentials, so a deactivated account can never receive a link, and the response text is identical either way (no account enumeration).

### 3. Scheduler

`Kernel::schedule()` was empty; it now registers `wms:hitung-replenishment` (daily 05:00), `wms:pengingat-harian` (weekdays 07:00), `wms:penyusutan-bulanan` (1st of month, 02:00), plus `queue:prune-failed` and `auth:clear-resets`. All three business jobs are `withoutOverlapping()->onOneServer()`. **`php artisan schedule:work` (or a cron entry) is now a deployment requirement** — without it the system is back to "only notices when a human clicks". Guarded by `::test_the_scheduler_registers_the_operational_jobs`, which shells `schedule:list` rather than reaching into the kernel (Laravel 12 has no `Kernel::getSchedule()`).

`wms:penyusutan-bulanan` defaults to **last month**, not the current one, since it runs on the 1st. The existing per-period idempotency inside `runAutomaticDepreciation()` means a re-run is safe.

### 4. Notifications

`App\Notifications\PersetujuanMenunggu` (approval queue) and `PengingatTenggat` (deadline digest), both `database` channel and both `ShouldQueue`. `App\Services\NotifikasiService` resolves recipients by role and **filters to `User::aktif()`** — a deactivated manager must not be handed approvals. Fired from `FakturPembelianController::store()` (→ Accounting Manager) and `MaterialRequestController::store()` (→ Purchasing + Accounting); the scheduler's digest covers the rest.

`PengingatTenggat` carries a `rincian` array so one notification summarises N items with a per-item signed day count, instead of spamming one row per overdue invoice.

**Reminder sources were extracted, not duplicated.** `invoiceJatuhTempo()`, `lotSegeraKedaluwarsa()`, `transferMenggantung()` plus the `susun()`/`urutkan()` builders moved out of `DashboardService` into the new `App\Services\PengingatService`; `DashboardService` now injects it and delegates. The dashboard panels and the scheduled digest are therefore the same implementation — the thresholds (`AMBANG_KEDALUWARSA_HARI`, `AMBANG_JATUH_TEMPO_HARI`) now live on `PengingatService` and `DashboardService` aliases them for backward compatibility. `PengingatService` also adds `transferTerlaluLamaMenggantung()` (in-transit aging, ≥3 days), `invoiceMenungguPersetujuan()` and `requestMenungguPersetujuan()`.

In-app UI: a lazy-loading bell in the navbar (`resources/js/notification-bell.js`, `Alpine.data('notifikasiLonceng')`) that fetches only when opened so no page pays extra queries, plus a full `notifikasi.index` page.

**`QUEUE_CONNECTION` must be a real driver with a running worker.** `.env.example` is now `database` and migration `2026_09_12_000004` creates `notifications`, `jobs`, and `job_batches` (all `if (!Schema::hasTable(...))`, framework tables so no `wms_` prefix). Verified end to end on real data: `wms:pengingat-harian` enqueued 5 jobs, `queue:work --stop-when-empty` drained them, and the rows landed as per-user unread notifications. **Watch out when testing this manually** — with a queue driver and no worker, notifications sit in `jobs` and the `notifications` table stays empty; that is correct behaviour, not a bug. The command's own output says "diantrikan", not "terkirim", for that reason.

### 5. Document attachments

`wms_lampiran_dokumen` (migration `2026_09_12_000005`) is polymorphic; `App\Models\Concerns\HasLampiran` is mixed into `FakturPembelian`, `PesananPembelian`, `PenerimaanBarang`, `PembayaranFaktur`, `ReturPembelian`, `PemeriksaanKualitas`, and `Aset`. `LampiranService::INDUK` maps a URL-safe key to each class and is the **whitelist** — the request never names a class, so no arbitrary model can be targeted.

**Storage decisions made here** (the two the survey said were needed): a dedicated private `lampiran` disk in `config/filesystems.php` rooted at `storage/app/lampiran`, swappable with one env var via `filesystems.lampiran_disk` (`LAMPIRAN_DISK=s3`); max **5 MB**; `pdf, jpg, jpeg, png, webp` only. The disk is private and files are served exclusively through the authorized `lampiran.download` route — never a public URL, which matters because these are invoice scans. A SHA-256 checksum is stored per file.

**Authorization is split deliberately.** Upload and download check `view` on the **parent document**; delete goes through `LampiranDokumenPolicy` and is restricted to **the uploader** (plus Super Admin via `Gate::before`). An earlier version tied delete to `update` on the parent and that was wrong: posted documents are immutable, so `update` is false for them, which would have made it impossible to attach or tidy evidence on exactly the documents that need evidence most — and an invoice scan normally arrives *after* posting. Evidence is not document content; do not re-couple these. A wrong file is superseded by uploading the right one.

UI is one reusable partial, `layouts/template/lampiran-panel.blade.php`, taking `induk`/`tipe`/optional `kategori`; wired into `aset/show` and `penerimaan_barang/show-page` (both eager-load `lampiran.user`).

`tests/Feature/PlatformHardeningTest.php` — 15 tests, deliberately a **new file** rather than more weight on the already-1519-line `WmsControlFrameworkTest`. Full suite 114 passing / 3109 assertions.

**Test gotcha worth knowing:** `actingAs()` leaves the session authenticated, so a later `post(route('login.attempt'))` hits the `guest` middleware and redirects to `RouteServiceProvider::HOME` (`/home`) instead of exercising login at all. The `cobaMasuk()` helper logs out and clears the rate limiter first. ### 7. `PenerimaanBarangService` extracted from the controller

`PenerimaanBarangController::store()` built inventory inline — it created `PenerimaanBarangDetail`, `LotPersediaan` and `LayerPersediaan` rows, called `StokGudangService`, drew down the PO, and posted the journal, all inside a `DB::transaction()` in the controller. ## Warehouse execution build — BUILT 2026-09-13

The whole "Warehouse / WMS execution" row of the open-items index, built in one pass. **The user's policy answers below are decisions, not defaults — do not re-litigate them.**

- **Cycle-count cadence: A monthly, B quarterly, C yearly.** Encoded in `AbcAnalysisService::SIKLUS_BULAN`.
- **Warehouses are at multiple physical sites, each with its own admin.** "Admin bisa melihat semua, gudang hanya bisa melihat gudang A dan admin yang lain hanya bisa melihat gudang B." Scoping is therefore **enforced**, not opt-in.
- **Approving a Material Request locks stock automatically, up to whatever is free.** A shortage locks the partial amount and lets approval proceed; it never blocks the approval.
- **Wanted now: wave picking and kitting. Not wanted: barcode/QR.** The user's words on QR: *"gapenting2 banget… nanti2 saja"* — plus one design note worth keeping: **QR would be per bundling/kit, not per item.** Do not build per-item barcodes if this is revisited.

### ABC classification — the foundation for cycle counting and slotting

`App\Services\AbcAnalysisService` classifies each (gudang, bahan) pair by **consumption value over the last 12 months**, sourced from `wms_pemakaian_barang_alokasi_stok.total_cost` joined to POSTED NPKs — the cost actually posted, not a recomputed `quantity × unit_cost`. Results land on `pengaturan_bahan_gudangs` (`kelas_abc`, `nilai_pemakaian`, `kontribusi_kumulatif`, `abc_dihitung_pada`), which was already the per-warehouse planning row. Command `wms:hitung-abc`, scheduled Mondays 04:00.

**The Pareto edge case, found by running it on real data and worth not re-introducing:** classifying on the cumulative share **including** the current item means that when the top item alone exceeds 80%, *nothing* is class A — the seed data produced exactly that (B and C only, no A). The fix is to classify on the cumulative share **before** adding the item, so the first item always lands in A and each item belongs to the class it starts in. `kontribusi_kumulatif` still stores the *after* value because that is what a human reads on a Pareto table. Guarded by `::test_abc_classification_puts_the_biggest_consumer_in_class_a`.

### Cycle counting

`App\Services\CycleCountService::mulai()` creates a DRAFT `StockOpname` seeded with **only the materials of one ABC class** that hold stock in that warehouse; `wms_stock_opname` gained `jenis` (`PENUH`/`SIKLUS`), `kelas_abc` and `zona`. Lines start at `physical_quantity = system_quantity`; the existing DRAFT→SUBMITTED→APPROVED→POSTED lifecycle and its `confirmPhysical` sign-off are unchanged, so nothing posts without a human confirming counts.

Due-date tracking needs no new table: `AbcAnalysisService::jatuhTempoSiklus()` reads `MAX(posted_at)` of POSTED `SIKLUS` opnames per (warehouse, class) and compares it to the class cadence. Board at `stock-opname.siklus`, also surfaced on the operator work queue.

**`StockOpname::$fillable` is a real list, not `$guarded`** — the three new columns had to be added to it. The first run silently wrote the DB default `PENUH` instead of `SIKLUS` because of this; the same mass-assignment failure mode as the `users.is_active` case in Tier 1. Check `$fillable` whenever adding a column to a model that uses it.

### Bin dimensions, volumetric capacity, slotting

`wms_lokasi_gudang` gained `panjang_cm`/`lebar_cm`/`tinggi_cm`/`kapasitas_volume_cm3`/`kelas_abc`/`urutan_pick`; `bahans` gained `volume_cm3`. `LokasiGudang::assertMuat()` now takes an optional `?Bahan` and checks **both** the pre-existing unit capacity and, when the bin has a volume (explicit or derived from dimensions) *and* the material has a per-unit volume, the volumetric fit. Both putaway and transfer receipt pass the material through. **Either check is skipped when its data is absent** — this stays backward compatible with bins that only ever had `capacity`, and with materials that have no volume recorded.

`App\Services\SlottingService::saran()` compares each material's ABC class against the ABC class of the bin it occupies and proposes a same-class bin that actually fits (it calls `assertMuat` on candidates rather than guessing). It is **read-only advice** — no automatic movement. A physical move still goes through the normal transfer/putaway path, which is what keeps layer values and the reconciliation invariants honest.

### Operator work queue

`App\Services\AntreanKerjaService::untuk($user)` + `antrean-kerja.index`: pending QC, pending putaway, open picks, inbound transfers awaiting receipt, and running opnames — every source filtered through `accessibleGudangIds()`, plus the user's waves and any cycle-count class that is due. This closes the "the whole `wms-control` prefix has exactly one GET route" complaint: an operator now has a page that answers "what is mine".

`User::accessibleGudangIds()` previously returned **every active warehouse** for `isWarehouse()`, with `pembagian_gudangs` constraining only Produksi. Now only SuperAdmin gets everything; both Warehouse and Produksi go through their assignments.

### QC re-inspection after a hold

`inspect()` accepted only `receiving_status === 'RECEIVED'`, so a receipt that ended in `QC_COMPLETED_WITH_HOLD` could never be inspected again. It now also accepts `QC_COMPLETED_WITH_HOLD` as a **follow-up pass**, which must name the exact lines it re-inspects (`$decisions` keyed by detail id) — a follow-up with no named lines is refused rather than silently re-deciding everything at "accept all".

A line whose layer is on QC hold is refused with a message pointing at **Pemeriksaan Consider**, which is the existing flow that resolves Consider-warehouse stock; QC re-inspection is not a second way to do that. The existing "already consumed" guard (`initial == remaining`) still blocks re-inspecting goods that have moved.

**Blind spot fixed while here:** a *partial* rejection puts the held quantity in a layer whose `source_type` is `QC_REJECT_{inspection}`, not `LPB_DETAIL`. The new end-of-inspection "is anything still on hold" check matches `source_id` against the LPB's details across **both** source types, so a follow-up pass cannot flip the receipt to a clean `QC_COMPLETED` while held stock remains. (Note `putaway()`'s own pre-existing hold guard still filters on `LPB_DETAIL` only — untouched here, but it is the same blind spot if it ever matters.)

### Auto-reservation on Material Request approval

`WarehouseExecutionService::reservasiOtomatis()` runs after `processApprove()` commits and reserves, per line, `min(jumlah_acc, stok bebas)` in the line's `tipe_gudang`. It returns a `dikunci`/`sebagian`/`gagal` tally that the JSON response summarises for the approver. **Deliberately partial and non-fatal**, per the user's choice: a shortage must not block an approval.

### Wave / batch picking

`wms_gelombang_pengambilan` + `gelombang_id`/`urutan_dalam_gelombang` on `wms_pesanan_pengambilan`. `GelombangPengambilanService` groups free picks (`RELEASED`/`PICKING`, same warehouse, not already in a wave) and orders them by **`LOKASI`** (minimum `urutan_pick` across the pick's bins — the travel-path heuristic) or **`BAHAN`**. Lifecycle `DIRENCANAKAN → DIRILIS → SELESAI`, with `DIBATALKAN` releasing the picks back to the pool. Completion is refused while any member pick is still open, so a wave cannot be closed over unfinished work.

### Kitting / bundling — deliberately a mini-BOM, not WIP

`wms_kit` (header, one output `Bahan`), `wms_kit_komponen`, `wms_perakitan_kit` + detail. `KittingService::rakit()` consumes each component through the normal FIFO `ambilLayer()`/`keluar()` path and creates **one new `LayerPersediaan` for the kit at exactly the summed component cost**, so value is conserved rather than invented. `urai()` is the inverse: it consumes the kit and returns components, splitting the kit's cost across them by quantity share. `WmsAccountingService::postPerakitanKit()` debits the kit category's inventory account and credits each component category's — and **returns null when every line nets to zero**, which is what happens when kit and components map to the same COA; the assembly is still recorded, there is simply nothing to journalise.

This is **not** BOM/WIP: no routing, no labour, no operations, no staged work-in-process. Those remain a separate design session. Kitting was built because the user asked for it explicitly, with that boundary stated up front.

### What was NOT built, and why

- **Cross-docking** — genuinely blocked, not skipped. Cross-docking routes received goods straight to an outbound shipment, and this system has **no outbound-to-customer side at all** (no Sales Order, no Surat Jalan). There is nothing to cross-dock *to*. It stays blocked behind the outbound domain listed under "New domains".

### Scope decisions already made (apply these to every remaining cluster)

- **Table prefix**: `wms_` prefix applies to domain/business tables only. Laravel framework tables (`users`, `password_reset_tokens`, `failed_jobs`, `personal_access_tokens`, `sessions`, `cache`, `jobs`, `migrations`) are left untouched — renaming those fights framework/package conventions (Sanctum, session driver, queue driver) for zero business value. `user_roles` also left as-is (tightly coupled to `users`/auth scaffolding).
- **Class suffixes stay in English**: `Controller`, `Policy`, `Request` (Store.../Update...), `Service`, `Factory`, `Seeder` are Laravel/artisan generator conventions, not business jargon — only the domain noun in the middle gets Indonesian-ized (e.g. `AssetController` → `AsetController`, not `AsetPengendali`).
- **Column names are mostly left alone.** Only rename a column when it's an identity/FK column that directly embeds the renamed entity's old abbreviation (e.g. `asset_number` → `nomor_aset`, `asset_category_id` → `kategori_aset_id`). Generic already-English columns (`name`, `status`, `amount`, `book_value`, `disposal_gain_coa_id`, etc.) are NOT translated — translating every column is an order of magnitude more scope (every Eloquent access, every Blade `{{ }}`, every Yajra column key, every seeder array key, every JS `row.xxx`) for little value versus the stated goal (kill confusing abbreviations, give tables/classes proper names).
- **Do NOT rename columns that a Yajra `datatables()->of(...)` JSON endpoint exposes to the `wmsDataTable()` Alpine JS layer** (e.g. `id_lpb`, `lpb_id`, `no_po`) — a mismatch there breaks the UI silently and is NOT caught by `php artisan test` (PHPUnit never touches the JS/Blade `x-for` row templates). This is why the LPB cluster below renames the table+model but keeps every column name identical.
- **Route model binding**: when a resource's URL segment changes (e.g. `lpb` → `penerimaan-barang`), use `->parameters(['penerimaan-barang' => 'lpb'])` to keep the internal binding variable name (`$lpb`) unchanged — this avoids having to rename every `$lpb`/`$asset` usage inside every controller method body. Only the type-hint class changes (e.g. `Lpb $lpb` → `PenerimaanBarang $lpb`).
- **Implicit `hasMany()`/`hasOne()` foreign-key guessing is a silent-breakage trap whenever the *declaring* model gets renamed.** Eloquent's default FK convention for these two relation types is `snake_case(<declaring class>) . '_id'` — NOT based on the related model, and NOT based on the column that already exists in the DB. Since this rename project deliberately keeps most FK columns unchanged (e.g. `service_category_id`, `invoice_lpb_id`), a relation that happened to omit an explicit FK argument because the *old* class name's snake_case form matched the real column by coincidence (`ServiceCategory`→`service_category_id`, `InvoiceLpb`→`invoice_lpb_id`) will silently start guessing the *new* wrong column the moment that class is renamed — no error until something actually queries through it (which may not be until a later cluster's seeder run exercises that code path, as happened here: two bugs from clusters 3/5 only surfaced during cluster 6's seed). **Before renaming any model class, grep that model file (and every other model that has a `hasMany`/`hasOne`/`morphMany` pointing *at* it) for relation calls with no second argument, and add the explicit FK.** `belongsTo()` is immune to this (its default FK is derived from the *method name*, not either class), so it's lower-risk but still worth a glance.
- **Verification per cluster**: after each cluster, run `php artisan migrate:fresh --seed --force`, then `php artisan test` (must stay 65/65 or whatever the current count is), then `composer test:case-sensitive`, then commit on the branch before starting the next cluster. Never leave more than one cluster's worth of breakage uncommitted.
- **MySQL's 64-character identifier limit** can silently reject an auto-named unique/foreign-key index once a table name grows from the `wms_` prefix + baku rename (hit this in the Npk cluster: `wms_pemakaian_barang_alokasi_stok_npk_id_inventory_layer_id_unique` = 68 chars). If `migrate:fresh` fails with "Identifier name ... is too long", give that `unique()`/`index()` call an explicit short name as the second argument.
